<a id="93-provisional-and-full-certification"></a>
#### 9.3 暫定認証と完全認証

*平易に言えば、システムは段階的に信頼を得る。新規システムおよび評価に失敗したシステムは、短い間隔の暫定認証から始まり、より頻繁に再確認される。現在問題がなく、問題が迫っている兆候もないシステムだけが、完全認証とより長い間隔に進む。評価に失敗すれば短い間隔に戻る。*

<a id="931-the-two-statuses"></a>
##### 9.3.1 二つのステータス

認証には二つのステータスのいずれかが付される。それぞれの認証間隔は異なり、[§8.1 記録の最低限の内容](#81-minimum-record-contents)に従ってシステム認証記録に記載する。

- **[暫定認証](core_05.040_band_continuity.md#provisional-certification)**は、次のシステムのステータスである。
  - 新たに導入されたシステムを含む、システムの初回認証；および
  - 再認証の失敗後、または再開審査もしくは新規審査で不整合が認定された後に認証されたシステム。

  暫定間隔は、同じシステム区分の完全認証間隔より短い。依拠の限度はシステム認証記録に記載する。
- **[完全認証](core_05.040_band_continuity.md#full-certification)**を得られるのは、暫定認証中のシステムの再認証時に限られ、次の三条件をすべて満たさなければならない。
  1. 求められる連続した「クリーン」な暫定再認証を完了していること。少なくとも一回であり、上位のシステム区分では採択文書が定める追加回数を要する；
  2. 現在の不整合がないこと。記録に未解決の不整合、未是正の欠陥、期限超過の確認、または失敗した回帰テストがない；および
  3. 不整合の切迫を示す監視指標がないこと。記録に定める監視トリガーと傾向指標が、閾値超過も閾値に向かう傾向も示していない。

完全認証はシステム区分に応じた認証間隔で運用される。時間制限があり、恒久的承認ではない。

再認証が条件2と3を満たす場合、その再認証は**クリーン**である。

<a id="932-failure-and-step-down"></a>
##### 9.3.2 失敗と降格

再認証、再開審査、または新規審査の結果によって、システムのステータスへの影響が決まる。

- 現在の不整合を認定した再認証は**失敗**である。[B部§7 認証結果](core_09.005_system_alignment_certification_record_process.md#7-certification-outcomes)の結果が適用される。次に取得できる認証は暫定認証に限られ、次の確認がどれほど良好でも変わらない。クリーンな再認証の回数はゼロから再開する。
- 現在の不整合はないが、切迫指標がある場合、再認証は失敗でもクリーンでもない。暫定システムは暫定のままで回数は進まない。完全認証システムは暫定へ降格する。
- [§9 再認証と再開](#9-recertification-and-reopening)に基づく再開審査で不整合が認定された場合、失敗した再認証と同じ効果が生じる。
- 認証を保有するシステムの新規審査で現在の不整合が認定された場合も同じ効果が生じる。認証ステータスのないシステムには[B部§7.4 拒否と取消し](core_09.005_system_alignment_certification_record_process.md#74-denial-and-revocation)の規則が適用される。

<a id="933-cause-of-misalignment"></a>
##### 9.3.3 不整合の原因

評価、再認証、再開審査、または新規審査が不整合を認定した場合、システム認証記録に原因を次のいずれかとして記載する。

- **設計原因：** システムまたはその手続が、意図どおりに運用しても不整合な結果を生むように構築されている；
- **運用原因：** 設計自体は妥当に見えるが、運用、入力、または維持の方法により結果が不整合になる；または
- **未決定：** フォーラムが原因を確定するまで、設計と運用の双方の是正策を保留する。

原因認定には次の限界がある。

- システムが不整合な結果を出し続けるなら、書面上の設計が妥当に見えても不整合である。妥当そうな設計は抗弁にならない。
- 不整合な結果を生む設計は、その結果が現れる前から不整合である。
- 原因認定は求める是正策と再開審査の範囲を定める。システムが不整合かどうかは決めない。

原因が設計にある場合：

- 再設計が実施され、検証されるまでクリーン再認証数はゼロのままである；
- 原因を認定したフォーラム、または[B部§6.2 監督の順序](core_09.005_system_alignment_certification_record_process.md#62-supervisory-sequence)に基づき次に指定されたフォーラムが、[該当する受付目標時間](core_05.040_band_continuity.md#tier-window)内に再設計を検証する。最初の暫定再認証時に行うこともできる；
- 再設計の検証前に行われた**構成要素評価**（認証回の一つの構成要素に関する評価部分。[B部§6.1 フォーラム監督と構成要素の役割](core_09.005_system_alignment_certification_record_process.md#61-forum-supervision-and-component-roles)が定義）は、どれほど良好でもクリーン総数に算入しない；および
- システムの運用方法を変えるだけでは、この段階を満たさない。

これらは上記の降格規則に追加されるもので、置き換えるものではない。運営者または影響を受けるsentientは、原因認定の再審査をフォーラムに求めることができる。原因が変更された場合、これらの規則は適用されなくなる。

<a id="934-tier-windows"></a>
##### 9.3.4 階層別の期間

初期評価、再認証、再開審査、または新規審査が不整合を認定した場合：

- [第十五章§6 適時解決、重要性階層、および遅延防止規律](core_15.000_forum.md#6-timely-resolution-materiality-tiers-and-anti-delay-discipline)の重要性階層に従って分類する；
- 原則としてシステム区分に合致する階層に置く（例：不整合なClass Aシステムは原則Tier A）；
- 受付、証拠保全、暫定保護、決定はその階層の期間および上限に従う；そして
- 超過は同節の定めにより審査する。

<a id="935-class-a-reliance"></a>
##### 9.3.5 Class Aの依拠

完全認証と比べ、暫定認証の間隔は短く、再認証がより早く到来する（[§9.3.1 二つのステータス](#931-the-two-statuses)）。依拠の限度はシステム認証記録に記載する（[§8.1 記録の最低限の内容](#81-minimum-record-contents)）。中断により代替策の到着前に生存必需品の供給が途絶える場合：

- 暫定認証だけを理由に、そのシステムを中断する必要はない；
- [B部§7 認証結果](core_09.005_system_alignment_certification_record_process.md#7-certification-outcomes)の暫定保護と認証条件がその事態を扱う；
- 設計原因の不整合が認定され、回数が保留されている間も同じである。回数の保留だけで、sentientsが依拠するシステムを中断することはない；および
- 保留中、フォーラムは暫定保護、依拠に関する認証条件、依拠者への通知を明示する。

<a id="936-verification-not-assertion"></a>
##### 9.3.6 主張ではなく検証

システムのステータス、クリーン再認証数、監視指標を検証し、その検証を独立審査に開く。システム自身の説明だけでは足りない。

- 不整合が決して現れないように指標を選定または設定してはならない；
- 再設計も他者が確認できる証拠に基づいて同様に検証する；
- 完全認証によって審査再開の理由が消えることはない。[§9 再認証と再開](#9-recertification-and-reopening)の全トリガーが引き続き適用される；および
- 回避は[§9.4 回避禁止](#94-non-evasion)に従って扱う。
