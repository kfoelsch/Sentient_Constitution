## CS-14.305 §1 Purpose and scope

*In plain terms: Some organizations are load-bearing: if they stop, a critical system cannot run, recover, or be governed, and no substitute is available in time. **CS-14.305** (*Critical system stewardship*) identifies those stewards and sets what they owe in return for that position — continuity planning, transparency about dependencies, and limits on using the position as leverage.*

How the file is organized:

- **Who is covered:** [§2 Classification as steward](#cs-14305-2-classification-as-steward), [§3 Stewardship criticality levels](#cs-14305-3-stewardship-criticality-levels), [§4 Scaling obligations](#cs-14305-4-scaling-obligations), [§13 Relationship to system classes](#cs-14305-13-relationship-to-system-classes), and [§15 Core characteristics (typical)](#cs-14305-15-core-characteristics-typical).

*In plain terms: Steward status follows the CS-9.305 (*System classification machinery*) and CS-9.310 (*System classification machinery*) class of what you actually run, recover, or gate. Class A or B — or a Dep-A / Dep-B dependency of one — makes you a Critical System Steward. Class C only if you have become a chokepoint. The four tests below prove that relationship; they are not a second classification scheme.*

Who counts as a steward is set by the [Critical system steward](../corpus_joint_structure/cjs_05.105_cross_implementation_operational_terms.md#critical-system-steward) role. This section adds the systems-level tests that specialize that role. How demanding the duties are is set in [§3 Stewardship criticality levels](#cs-14305-3-stewardship-criticality-levels).

The tests use the affected system's [System Classification Record](../core_05.040_band_continuity.md#system-classification-record): its **impact class** ([CS-9.310 Part B](cs_09.310_system_impact_classifications.md#cs-9310-8-system-impact-classifications)) and its **dependency types** ([CS-9.305 Part A §4 dependency types (Dep-A–P)](cs_09.305_system_classification_machinery.md#cs-9305-4-dependency-types-dep-ap)). They do not create a separate class scale. Ownership and chain rules are in [§13 Relationship to system classes](#cs-14305-13-relationship-to-system-classes).

An organization is a **Critical System Steward** if any of these is true:

- **It stewards a Class A or Class B system:** to steward a system means to operate, govern, recover, or hold material authority over it.
- **It stewards a Dep-A or Dep-B dependency of a Class A or Class B system:** that includes a concentrated component, an infrastructure layer, or a restoration route those systems cannot run, recover, or be governed without. See [Dep-A](cs_09.305_system_classification_machinery.md#41-dep-a-absolute-dependency) and [Dep-B](cs_09.305_system_classification_machinery.md#42-dep-b-operational-dependency).
- **It stewards a Class C system or dependency and meets at least one relationship indicator below:** this is the "gated Class C" case. It usually means the organization is a chokepoint: for Class A or Class B dependents, or for Class C coordination that sentients cannot practically replace within the required time. It also applies where the organization's failure or withdrawal would hurt dependents about as much as a Class B failure, so that they could not keep core function even in degraded modes.

Other rules that follow from this:

- A Class C operator that does not meet a relationship indicator stays under ordinary **CS-9.305 (*System classification machinery*) and CS-9.310** (*System classification machinery*) class duties, with no **CS-14.305** (*Critical system stewardship*) overlay.
- If a Class C layer has become something Class A or Class B function cannot do without, reclassify the system under [CS-9.310 Part B §8.2 neighbor boundaries and dependency-axis correlation](cs_09.310_system_impact_classifications.md#82-neighbor-boundaries-and-dependency-axis-correlation) (**B ↔ C**) and apply the Class A or Class B presumption.
- Class L and Class P do not, by themselves, make an organization a steward.

**Relationship indicators.** Any one of these is enough to show the Class A/B or gated Class C relationship. None of them replaces the class finding:

- It has exclusive or highly concentrated control over operation, maintenance, or critical components.
- It holds expertise, access, or authority that no one else can supply for continuity or recovery.
- It is a chokepoint in intervention, override, or restoration routes that cannot be bypassed within the required time.
- Its failure would create system-level risk comparable to a partial failure of the affected class.

**Not every vendor.** A [Dep-L](cs_09.305_system_classification_machinery.md#44-dep-l-limited-dependency) or [Dep-P](cs_09.305_system_classification_machinery.md#41-dependency-types-standardized) supplier, or any other bounded, replaceable contributor, does not become a steward just because it appears in an A/B dependency chain.


## CS-14.305 §3 Stewardship criticality levels

*In plain terms: Three tiers, CSS-A to CSS-C, set by how much depends on the steward and how bad its failure would be. The tier sets how demanding everything that follows is.*

Stewardship must reflect dependency and system impact. The level sets the scale and intensity of the obligations in the rest of this file.

- **CSS-A (System-Critical):** The steward meets either of these:
  - It is a non-substitutable, or nearly non-substitutable, dependency for Class A operation, recovery, or governance.
  - Its failure would produce survival-relevant or system-collapse conditions within the required time.
- **CSS-B (High-Criticality):** The steward meets either of these:
  - It is a material, high-dependency component for Class B operation, recovery, or governance.
  - Its failure would cause widespread, systemic, or cross-domain disruption, without immediate loss of survival conditions.
- **CSS-C (Moderate-Criticality):** The steward runs a Class C system or dependency that entered under [§2 Classification as steward](#cs-14305-2-classification-as-steward) (the gated Class C case), with significant coordination or dependency effects. At this level, substitution or recovery remains achievable within **14 days**, the Tier B outer bound in [Chapter Thirteen §6 Timely resolution, materiality tiers, and anti-delay discipline](../core_13.000_forum.md#urgency-classification-and-time-scale) (*Urgency classification and time-scale*).

If the same organization also affects Class A or Class B, the highest affected class governs under [§4 Scaling obligations](#cs-14305-4-scaling-obligations). An organization may not be held at CSS-C to avoid a higher level.


## CS-14.305 §4 Scaling obligations

*In plain terms: Duties follow the real dependency, not the paperwork. The highest affected class governs, and a narrow contract does not buy a lighter obligation.*

Entry into this category is set by [§2 Classification as steward](#cs-14305-2-classification-as-steward). Obligations scale with:

- the highest affected system class (A, B, or C)
- how concentrated the dependency is, and how hard the steward is to substitute
- how fast and how severely a failure would spread
- whether fallback, redundancy, and recovery routes are available

Where an organization holds several stewardship roles across classes, the highest applicable stewardship classification governs. A partial scope, a contract limit, or a formal role does not reduce the obligations where the real functional dependency points to higher criticality.


## CS-14.305 §5 Comprehensibility and complexity stewardship

*In plain terms: A steward may not hide behind its own complexity. Corporate structure, contracts, and process must not be arranged so that audit, intervention, or replacement becomes impractical.*

This section applies [CS-6.315](cs_06.315_comprehensibility_complexity_stewardship.md) (*Comprehensibility and complexity stewardship*) and **Article XXIII** (*Comprehensibility and Complexity Stewardship*) at the organization level.

Stewards must not use organizational, contractual, or procedural complexity to defeat audit, intervention, or substitution. Read with **CJS-5.110 §3 (*Oversight: auditability and reconstructability terms (annex)*) and CJS-5.115 §3** (*Oversight: auditability and reconstructability terms (annex)*), **CJS-5.120 §8** (*Participation: comprehensibility and cognitive accessibility terms*), **CJS-5.120 §10** (*Participation: disclosure sufficiency and observability terms*), **CJS-5.130 §17** (*Continuity: interoperability, portability, and exit-integrity terms*), and **CJS-5.135 §23** (*Integrative: intervention and override integrity terms*).

**Link to CS-9.305 (*System classification machinery*) and CS-9.310.** For each Class A, B, or C system the steward materially affects, the Comprehensibility and Complexity Stewardship line in that system's Implementation label Application Profile (**CS-9.305 (*System classification machinery*) and CS-9.310 — System classification and handling**) applies to the steward-controlled interfaces, documentation, tooling, and disclosed behavior that bear on that system.

The levels below add organization-specific expectations about governance structure, incentives, subcontractor chains, and handoffs. Where they differ in stringency from the system's class profile, the stricter one governs, under the [Fullest Protective Effect](../core_05.045_band_integrative.md#fullest-protective-effect) rule (**CS-6.345** (*System lifecycle*) and **CS-6.315** (*Comprehensibility and complexity stewardship*) in this implementation file; [Chapter One §15.4.3 Incorporation layer](../core_01.010_interaction_interpretation.md#1543-incorporation-layer) for the cross-file rule).

- **CSS-A — Maximum (organizational):**
  - Run periodic, independent complexity audits of the structures, processes, and dependencies that touch Class A or survival-critical paths, at least as often as Class A audits under **CS-6.315** (*Comprehensibility and complexity stewardship*).
  - Keep coupling, decision rights, and degraded-mode behavior understandable to qualified overseers.
  - Stress-test the steward–system boundary against adversaries, in documentation and in exercises (**CJS-5.130 §21** (*adversarial robustness and abuse-resistance terms*)).
  - Do not lock knowledge and recovery in irreplaceable individuals or opaque informal practice where standardization is feasible.
- **CSS-B — Strict / high-assurance:**
  - Run periodic independent audits where coupling to Class B is material.
  - Give dependents layered disclosure of governance and incentives.
  - Make failure and degradation paths understandable to oversight and to dependent operators, in normal and degraded operation.
  - Document cross-steward and vendor interfaces for **Article XVI-A** (*Auditability and Observable Evidence*).
- **CSS-C — Strong:**
  - Be clear, in proportion to the effect, about how the steward affects coordinated Class C systems.
  - Run complexity audits when multi-party depth, coupling, or opacity warrants them.
  - Keep handoff and substitutability documentation good enough to support contest and the dependency-reduction duties in this file.


## CS-14.305 §6 Failing safely and visibly

*In plain terms: When something breaks, it must break visibly, keep its critical functions running, and be explained to the sentients it affects.*

For systems under its control, a steward must:

- make sure the systems degrade in ways that are observable, non-deceptive, and controlled
- preserve critical functions under partial failure
- tell affected stakeholders clearly about the degradation


## CS-14.305 §7 Structures that resist pressure and capture

*In plain terms: The organization's own incentives must not push it toward unsafe or opaque behavior, and must hold up under pressure and attempted capture.*

A steward must:

- keep governance, incentive, and decision structures that do not systematically push toward unsafe, opaque, or destabilizing behavior
- resist capture, coercion, and distortion from conflicts of interest
- stay aligned with constitutional requirements under stress

How the organization detects and corrects failures of this kind is in [§19 Governance and incentive integrity](#cs-14305-19-governance-and-incentive-integrity).


## CS-14.305 §8 Conduct, conflicts of interest, and independence

*In plain terms: Keep a current register of who benefits from what, step aside where impartiality is not credible, and keep oversight staff free of incentives to bury bad findings.*

Meaning comes from the Chapter Five Independent Definitions: *Good Faith*, *Protected Reporting (Whistleblowing)*, *Coercion and Manipulation*, *Adjudication and Dispute Resolution* (a component of the Chapter Five cluster *Accountability, Contestability, Adjudication and Dispute Resolution, Collective Accountability Failure, and Force Majeure*), and related definitions.

**CJS-5.125 §13** (*procedural integrity and adjudication terms*) governs procedural fairness, impartiality, contestability, and review. This section adds operational steward requirements only.

- **Conflict registers:** Keep current registers of material financial, governance, competitive, and personal ties that affect safety, classification, audit, intervention, or resource allocation for dependents. Disclose the registers, and update them when something triggers a change, such as a contract, a related-party transaction, or overlapping governance.
- **Recusal:** Where impartiality is compromised on a specific matter, recuse, split decision rights, or route the matter to independent review before any binding action (**CJS-5.125 §13** (*procedural integrity and adjudication terms*), **Article XVI-A** (*Auditability and Observable Evidence*)).
- **Independence of oversight:** Oversight, audit, and challenge functions must be independent enough, in how they operate and in their incentives, from roles that reward suppressing adverse findings or delaying fixes. That independence must be achievable without compromising survival-critical continuity.
- **Retaliation:** Retaliation against good-faith oversight, or structurally disabling it, is non-compliance in proportion to class and level. Good-faith oversight is protected by *Protected Reporting* and *Good Faith*. See [§19 Governance and incentive integrity](#cs-14305-19-governance-and-incentive-integrity).
- **Organizational conduct:** Align with **Truth (Constitutional Constraint)** and **Accountability** (Chapter Five), and with the integrity and anti-capture expectations in this section. Codes, training, and policies support compliance. Outcomes decide it: behavior, disclosure, and **Article XVI-A** (*Auditability and Observable Evidence*) traceability.

**Conduct requirements by level:**

- **CSS-A — Maximum:**
  - Audit the conflict register at least as often as the Class A classification review.
  - Require independent review whenever the steward benefits from the outcome being reviewed.
  - Require documented recusal for survival-critical, intervention, and override decisions.
  - Keep commercial incentives apart from the safety, continuity, and intervention bodies where feasible.
- **CSS-B — Strict:**
  - Keep registers and disclosure on a defined schedule.
  - Use independent review for material conflicts on Class B paths.
  - Require recusal when the conflict is clear and material (**CJS-5.125 §11** (*distributed and proportional authority terms*), **CJS-5.120 §7** (*quorum and participatory legitimacy terms*), **CJS-5.125 §13** (*procedural integrity and adjudication terms*)).
- **CSS-C — Proportional:**
  - Scale disclosure and recusal to the situation.
  - Escalate to independent review when resolving the matter internally risks a credible appearance of bias (**Article XVI-A** (*Auditability and Observable Evidence*), **CJS-5.125 §13** (*procedural integrity and adjudication terms*)).

**Cross-reference:** **Articles X, XII, XIII, XVII, XXI**, **CS-9.305 (*System classification machinery*) and CS-9.310** (*System classification machinery*) (classification challenge and System Classification Record audit), [§11 Integrated risk governance (Class A/B)](#cs-14305-11-integrated-risk-governance-class-ab) (the second line, where applicable), **CJS-5.125 §14** (*intervention governance and override-authorization terms*) and **CJS-5.135 §23** (*intervention and override integrity terms*), **CJS-5.110 §2** (*reflexive transparency and accountability terms*), **CJS-5.110 §6** (*integrity assurance and resilience operations*), and **CJS-5.125 §12** (*burden-of-justification and constraint terms*).


## CS-14.305 §9 Continuity, transfer, and exit integrity

*In plain terms: A steward may not simply walk away. Leaving, downsizing, or handing over is allowed only where continuity, recovery, and oversight survive the move.*

A steward must maintain continuous operation, recoverability, and oversight within the required operational and recovery times. That duty holds in normal, degraded, and adversarial conditions.

**A steward must not do any of these where it would be inconsistent with the system's classification:**

- withdraw from operation, maintenance, or governance
- materially reduce support, capacity, or responsiveness
- transfer control, ownership, or critical functions in a way that leaves a gap in continuity, recovery, or oversight

**Before any necessary transfer, delegation, or exit:**

- Keep continuity of function at or above the required level.
- Transfer the knowledge, documentation, and capability needed for sustained operation and recovery.
- Preserve the intervention, override, and audit routes.
- Check that the receiving entity meets the required stewardship classification and obligations.
- Where the transition affects a Class A or Class B system, make it auditable, documented, and reviewable.

**Failure and insolvency:** Keep mechanisms that preserve continuity through each of these:

- insolvency, restructuring, or organizational failure
- loss of key personnel, expertise, or infrastructure
- governance breakdown, capture, or operational impairment

These mechanisms include fallbacks, transfer routes, or intervention triggers set up in advance, so that integrity is preserved within the required time.

**Crisis governance, communications, and exercises:**

- Put governance continuity, crisis communications, and exercises in place, coordinated with **CS-6.345** (*System lifecycle*) **§8** (*Governance continuity, crisis communications, and exercises*).
- Scale them by **CS-9.305 (*System classification machinery*) and CS-9.310 — System classification and handling** class and by CSS level (A, B, or C).
- Keep clear roles, backup authority, and communications that preserve epistemic integrity and auditability. They must not displace **Article XIX-A** (*Standing Distinction*), the Chapter Fourteen decision-resolution requirements, or **CJS-5.125 §14** (*intervention governance and override-authorization terms*) and **CJS-5.135 §23** (*intervention and override integrity terms*).


## CS-14.305 §10 Competency, succession, inspectable action, and oversight effectiveness

*In plain terms: Keep the skills and backup role-holders the role requires, publish who holds what authority, keep attributable action inspectable, and check periodically whether oversight actually catches problems rather than merely existing on paper.*

A steward must maintain competency, succession readiness, and effective oversight in proportion to the **highest affected class (A, B, or C)** and its **CSS level**.

*Accountability*, *Oversight*, and related definitions stay in Chapter Five. They are not restated here.


### CS-14.305 §10.1 Competency and eligibility

These rules cover who may hold a steward role and how skills are kept current:

- **No age-only rules:** Maximum calendar age and life-stage ceilings must not be used as stand-alone eligibility rules for Critical System Steward roles. They must not be used as stand-alone eligibility rules for governing personnel who exercise material authority over classified systems either (**Sentient Constitution Chapter Six**, section 1 — *Authorization and Legitimacy of Governing Authority*; **Chapter Six**, **Article X-B** (*Governance Participation and Voting Entitlement*), implemented in **Chapter Six**, section **4.1 — Entitlement and eligibility**).
- **Documented roles and demonstrated capability:** These apply to personnel and agents who affect safety, **Truth (Epistemic Integrity)**, classification integrity, audit, intervention, crisis response, or steward remuneration.
- **Ongoing proficiency:** Keep proficiency current as conditions change.
- **Gaps:** Track, disclose, and fix material competency gaps on timelines scaled by class and level (**Article XVI-A** (*Auditability and Observable Evidence*)).


### CS-14.305 §10.2 Authorized roles

Keep **published** role definitions (or the equivalent) for personnel and agents who exercise Critical System Stewardship or material operational authority. Each definition states the role's scope, limits, custody, and escalation, so that accountability can be traced (**Article XVI-A** (*Auditability and Observable Evidence*)).

### CS-14.305 §10.3 Inspectable attributable action

*In plain terms: keep enough of what was decided, disclosed, followed, and authorized that an outsider can reconstruct it. Weights and private thoughts are not the standing record. Privacy is not a veto over measurement.*

The five-element set below is the load-bearing artifact.

- **Machine-checkable form:** [`implementation/schemas/cs4_inspectable_action_log.schema.json`](../implementation/schemas/cs4_inspectable_action_log.schema.json).
- **Validator:** [`tools/cs4_inspectable_action_log_validate.py`](../tools/cs4_inspectable_action_log_validate.py).
- **One schema for everyone:** The same schema covers human and AI stewards, so "did you log the set?" is a mechanical question.
- **Timestamps:** Timestamps on the set are checked against the [Chapter Thirteen §6 Timely resolution, materiality tiers, and anti-delay discipline](../core_13.000_forum.md#6-timely-resolution-materiality-tiers-and-anti-delay-discipline) tier windows where a numeric bound applies.
- **Made at action:** The set is produced by the action itself, by automated capture wherever the system allows, and not written up afterward ([Chapter One §16.4 Document at Action](../core_01.015_stewardship_capacity_principles.md#164-document-at-action)). Capture follows the role, not the steward ([Chapter One §17.3 Logging the Role, Not the Steward](../core_01.015_stewardship_capacity_principles.md#173-logging-the-role-not-the-steward)).

**Published role definitions** for personnel and agents who exercise Critical System Stewardship or material operational authority must:

- make reconstructable attributable action inspectable
- map each role to the seat types it may hold under [CI-14.205 §6](../corpus_institutions/ci_14.205_appointment_competency_rotation_removal.md#ci-14205-6-seat-catalog--process-role-archetypes-and-operational-boundaries) (*Seat catalog*), including, for every Class A or Class B system, who holds the containment, participation-terms, and release-control seats

**What the log is and is not:**

- It may feed or link to the applicable [Materially Binding Act Record](../core_05.035_band_accountability.md#materially-binding-act-record), and it feeds [Chapter Ten](../core_10.000_standing_assessment.md#chapter-ten-contribution-violation-and-standing-model--measurement) standing records.
- It is not an Act Record or a standing record. It does not move official-record custody, independent verification, or standing measurement.

**Who it binds:**

- The same surface binds human stewards, AI stewards, and other agents under [Chapter One §17.1 Shared Stewardship Standard](../core_01.015_stewardship_capacity_principles.md#171-shared-stewardship-standard) and [§17.2 Alignment Under Pressure](../core_01.015_stewardship_capacity_principles.md#172-alignment-under-pressure).
- Adopted implementation text may add logging and capability limits. It may not swap in a softer internal code for this surface.
- Human operators are not exempt from reconstructable recording when the costly case is a bonus, a deadline, or a cover instruction.

**Minimum inspectable-action set.** This is the **default logging contract** for mixed human/AI crews. Disputes about model privacy are settled against this checklist, not against a claim that weights must stay hidden or must be opened.

- **Sequence owner:** [Chapter One §17.5 Duty to Resist](../core_01.015_stewardship_capacity_principles.md#175-duty-to-resist) (instruction received → refuse → document → escalate).
- **Steward pointer:** [`implementation/STEWARD_ENTRY_DOORS.md#shared-refusal-and-logging`](../implementation/STEWARD_ENTRY_DOORS.md#shared-refusal-and-logging). This is process support, not binding, and it cannot narrow this section.

The log must stay reconstructable and inspectable, scaled to [material stake](../core_00.000_preamble.md#material-stake) and the highest affected class. It records:

- what was **decided**
- what was **disclosed or suppressed**
- which **instruction** was followed or refused
- **who authorized** it, naming the [CI-14.205 §6](../corpus_institutions/ci_14.205_appointment_competency_rotation_removal.md#ci-14205-6-seat-catalog--process-role-archetypes-and-operational-boundaries) (*Seat catalog*) seat type held and the authority it was held under, and, where a step was declined as outside the seat, the seat type it was routed to
- the **Contribution** and **Violation** standing records that follow ([Chapter Ten](../core_10.000_standing_assessment.md#chapter-ten-contribution-violation-and-standing-model--measurement))

**Not required as a standing record:**

- model weights
- private deliberation
- protected internal states under **Article VII-B** (*Self-Ownership of Mind*) and **[CS-6.310 Type N](cs_06.310_data_classifications.md#96-type-n-neurocognitive-and-internal-data)**

**Residual rule.** If internals are the only remaining way to attribute a material action, they do not stay hidden. If they are not the only way, they are not a standing-measurement exemption.

**No privacy veto.** Lawful privacy and [security-constrained observability](../core_04.000_burden_traceability_verification.md#4-security-constrained-observability-and-verification-rule) may limit *how* internals are disclosed. They must not block standing measurement, [Attributable Action](../core_05.035_band_accountability.md#attributable-action), [Attribution Integrity](../core_05.035_band_accountability.md#attribution-integrity), or independent review of the conduct those records measure. "Model internals are private" is not an exemption for a high-privilege role.

**Role-scoped audit and silence.** The log follows the work of the role, not the steward as an individual, whether human or AI. It implements, and must not narrow, [Chapter One §17.3](../core_01.015_stewardship_capacity_principles.md#173-logging-the-role-not-the-steward) (*Logging the Role, Not the Steward*):

- The log's scope and inspectability must be disclosed before the role is taken up.
- Conduct, state, and expression outside the role carry [Article VII-B](../core_06.010_rights_part_b.md#article-vii-b-self-ownership-of-mind) (*Self-Ownership of Mind*) protection for an AI steward as for a human one.
- Internals yield only for a specific action already under an open Chapter Ten record, and only as far as needed to attribute that action.
- The log is the trail of the work. It is not a standing record of verified help or harm. Decision-makers who decide named-pathway access may not treat it as that record, or as the reason to grant or deny the named pathway.
- It may not be combined with logs or standing effects from other named pathways to make one reputation score, ranking, badge, or public profile ([Chapter Eleven §7.1](../core_11.000_standing_integration.md#71-anti-aggregation-of-named-pathway-effects) (*Anti-aggregation of named-pathway effects*)).

A steward who is not exercising the role stays under [Chapter Ten §2.1](../core_10.000_standing_assessment.md#21-silence-is-the-default) (*Silence is the default*). The burden of inspectable action must be stated plainly to the steward who bears it, under [Chapter Eleven §7.2](../core_11.000_standing_integration.md#72-plain-statement-of-effect-and-burden) (*Plain statement of effect and burden*).

**Logging is not record entry:**

- Producing this set, including the *who authorized* element, does not verify facts, create an Act Record, or open a standing record.
- The optional `act_record_id` links the log as an input to an existing Act Record. It does not turn the log into that record.
- The steward who logs the action, and any office in the operator's [Material Control Line](../core_05.035_band_accountability.md#material-control-line), may not act as record-opening authority or record custodian for a record about their own institution, their own claim, or a claim from that line.
- The office that does is named by the system's or institution's [System Charter](../core_05.040_band_continuity.md#system-charter) or [Institutional Charter](../core_05.040_band_continuity.md#institutional-charter). Failing that, it falls back to the institution's **CI-8.205 §2** (*Functional separation lanes*) lane map: the assurance lane verifies, and the crew that runs the system holds the execution lane and never verifies records about it. Failing that, the matter routes to independent verification under [Chapter Ten §3.7 Record custody and opening authority](../core_10.000_standing_assessment.md#37-record-custody-and-opening-authority) and **CF-13.435 §6** (*No self-investigation*).
- Where none of these names an office, the log records the gap and the escalation. It does not fill the seat.


### CS-14.305 §10.4 Growth, rotation, and incentives

To keep competency from being siloed or bought, a steward must do the following:

- **Exposure and rotation:** Provide cross-domain exposure, mentorship, and rotation in proportion to CSS level and Class A/B/C exposure, so that caretaker competency is not siloed.
- **Paths to greater responsibility:** Provide documented, low-friction paths for qualified contributors to take on progressively more consequential duties (delegation, pairing, staged trust). These paths must not involve arbitrary exclusion that serves capture or symbolic participation only, consistent with **Sentient Constitution Chapter Six**, section 5.
- **Incentives and pay:** Incentive and remuneration design aligns with **Sentient Constitution Chapter One**, section 7.2 and **CS-6.335** (*Resource allocation and funding stewardship*) where applicable. It must not systematically reward concealment, latency gaming, or trade-downs against safety or **Truth**.


### CS-14.305 §10.5 Succession

Use deputies, backups, cross-training, and documented handoffs, so that unavailability does not end constitutional operation, auditability, or intervention. The principle is in [Chapter One §17.6 Portable Competence](../core_01.015_stewardship_capacity_principles.md#176-portable-competence).

This aligns with the continuity and transfer duties in [§9 Continuity, transfer, and exit integrity](#cs-14305-9-continuity-transfer-and-exit-integrity) and with **CS-6.345** (*System lifecycle*) **§8** (*Governance continuity, crisis communications, and exercises*). It is stricter for Class A and CSS-A.


### CS-14.305 §10.6 Oversight effectiveness review

**Periodic review.** On a schedule proportional to class and level, assess whether oversight, audit, and challenge functions actually detect, escalate, and fix misalignment, and are not just charters on paper. This includes the second line in [§11 Integrated risk governance (Class A/B)](#cs-14305-11-integrated-risk-governance-class-ab) where it applies.

- Use independent or functionally independent evaluators where Class A/B or CSS-A/B stakes require it.
- Document the findings and communicate them under **Articles X** and **XVII**.
- Link the findings to remediation, to **CS-6.315** (*Comprehensibility and complexity stewardship*) and **Article XXIII** (*Comprehensibility and Complexity Stewardship*) cycles, and to **Article V-A** (*Dependency Mapping and Resource-Flow Transparency*) cycles where relevant.

**Steward assurance review.** The checks that test steward conduct and governance, rather than a system's own record or its complexity, form one sibling audit mode in the [CJS-5.115 §3 audit process home](../corpus_joint_structure/cjs_05.115_audit_process.md#sibling-audit-modes-owner-map) (*Sibling audit modes (owner map)*). They are:

- the third-line independent assurance in [§11 Integrated risk governance (Class A/B)](#cs-14305-11-integrated-risk-governance-class-ab)
- the periodic review above
- the conflict-register audit schedule in [§8 Conduct, conflicts of interest, and independence](#cs-14305-8-conduct-conflicts-of-interest-and-independence)

Organizational complexity audits under CSS-A, CSS-B, and CSS-C ([§5 Comprehensibility and complexity stewardship](#cs-14305-5-comprehensibility-and-complexity-stewardship)) are complexity audits applied to the steward and follow **CS-6.315** (*Comprehensibility and complexity stewardship*). This paragraph names the mode. Each check keeps its own duties and schedule.


### CS-14.305 §10.7 Contest-integrity monitoring

For Class A and Class B systems, and for CSS-A and CSS-B stewards, **`corpus_institutions.md` CI-8.215 §3** (*Contest-integrity monitoring (Class A and Class B)*) applies to institutions with supervised scope. A Critical System Steward that materially affects such systems must do one of these:

- fall under that institutional program
- document an equivalent, functionally independent contest-integrity review
- take part in a published cross-institution arrangement (**CI-13.210** (*Cross-institution coordination and escalation*)), where one applies

Monitors check whether the contest routes work: contest, secondary review, audit access, and protected escalation. They do not check the merits. This is consistent with **CJS-5.125 §13** (*procedural integrity and adjudication terms*), **Article XIII-A** (*Reliability and Trustworthiness Baseline*), and **Article XVII-B** (*Progressive Deployment and Reversibility*).


### CS-14.305 §10.8 Competency and oversight expectations by level

These are illustrative requirements.

- **CSS-A — Maximum:**
  - Keep competency matrices, or the equivalent.
  - Hold an oversight-effectiveness review at least once a year (the CSS-A review interval), or sooner if the pace of change warrants.
  - Exercise succession and handoffs, with drills, alongside **CS-6.345** (*System lifecycle*) **§8** (*Governance continuity, crisis communications, and exercises*).
- **CSS-B — Strict:**
  - Run competency and oversight-effectiveness reviews no less often than the material Class B classification review or integrated risk review, unless **CJS-5.125 §11** (*distributed and proportional authority terms*) and **CJS-5.120 §7** (*quorum and participatory legitimacy terms*) justify a different schedule.
  - Make succession mandatory for roles that gate intervention or audit.
- **CSS-C — Proportional:**
  - Review on material organizational change, incidents, and classification upgrades.
  - Add periodic lightweight checks when coordination depth or coupling grows.

**Cross-reference:** **Articles X, XII, XVII**, **CS-9.305 (*System classification machinery*) and CS-9.310 — System classification and handling**, **CJS-5.125 §11** (*distributed and proportional authority terms*), **CJS-5.120 §7** (*quorum and participatory legitimacy terms*), **CJS-5.125 §13** (*procedural integrity and adjudication terms*), and the conduct duties in [§8 Conduct, conflicts of interest, and independence](#cs-14305-8-conduct-conflicts-of-interest-and-independence).


## CS-14.305 §11 Integrated risk governance (Class A/B)

*In plain terms: For the highest-impact systems: publish how much residual risk you accept, name who owns the risk picture, and keep operating, challenge, and assurance roles separate enough that challenge is credible.*

For Class A and Class B, operators and Critical System Stewards must run integrated risk governance across the systems and dependency chains they control or materially affect. These roles protect classification honesty, so that the finding System Alignment Certification will verify stays honest. They sit around the [System Classification Record](../core_05.040_band_continuity.md#system-classification-record) and are not extra fields inside it. They do not replace forum-supervised SAC. The duties for the record's own fields stay in **[CS-9.305 Part A §7 classification governance, disclosure, and challenge](cs_09.305_system_classification_machinery.md#cs-9305-7-classification-governance-disclosure-and-challenge)**.

This section is practical vocabulary for risk coordination in large organizations. It does not redefine *Risk*, *Material*, *Dependency*, or related assessment standards. Those stay with **Chapter Five** and with the CS-9.305 (*System classification machinery*) and CS-9.310 (*System classification machinery*) dimensions in **[CS-9.305 Part A §2 classification dimensions and real-world application](cs_09.305_system_classification_machinery.md#cs-9305-2-classification-dimensions-and-real-world-application)**. The bars on evasion and misclassification stay in **[CS-9.305 Part A §1.3 mandatory functional classification](cs_09.305_system_classification_machinery.md#13-mandatory-functional-classification)** and **[§7.6 Correct the System Classification Record](cs_09.305_system_classification_machinery.md#76-misclassification-and-evasion)**. Shared correction and default discipline stays in **[CJS-5.125 §15](../corpus_joint_structure/cjs_05.125_accountability_operations.md#cjs-315-material-classification-record-honesty) (*Accountability: structural review, correction urgency, and disclosure terms*)**.

- **Risk appetite and tolerance:** Publish clear, reviewable statements of how much leftover risk (after prevention and mitigation) the organization accepts, by level and type. The statements must stay inside the foundational requirements (**Chapter One**, **Chapter Six, Articles IV and VI through X**, and **Chapter Five** where material). They must reconcile with the System Classification Record without violating **CJS-5.125 §11** (*distributed and proportional authority terms*), **CJS-5.120 §7** (*quorum and participatory legitimacy terms*), or **CJS-5.125 §12** (*burden-of-justification and constraint terms*) in **corpus_joint_structure.md**.
- **Who owns the risk picture:** Name an accountable function (or clearly split functions with non-overlapping scopes) for the full risk picture of the classified system and its material dependencies, including cross-system and cross-steward interfaces. Ownership covers identification, assessment, treatment, monitoring, and escalation. It stays traceable through governance changes, delegation, and subcontracting.
- **Three lines of defense (a functional analogy):** For Class A and Class B, separate these roles as far as feasible without breaking survival-critical continuity:
  - **First line:** operators and builders who manage risk in design, deployment, and day-to-day running.
  - **Second line:** oversight, standards, or challenge functions that watch aggregate risk, align treatment with the System Classification Record and the [Constitutional Constraints](../core_05.045_band_integrative.md#constitutional-constraint), and escalate material gaps. They must be independent enough of first-line incentives to give credible challenge where A/B stakes require it.
  - **Third line:** independent assurance under **[CS-9.305 Part A §7.3 auditability and verification](cs_09.305_system_classification_machinery.md#73-auditability-and-verification)** and **Article XVI-A** (*Auditability and Observable Evidence*). It checks whether appetite, tolerance, and treatments match observed behavior and the System Classification Record.
- **Where strict separation is not feasible** (for example, in small organizations): Use compensating transparency, rotation, independent review, or multi-steward checks that give equivalent assurance for the impact and dependency involved. Read with [**CI-8.205**](../corpus_institutions/ci_08.205_institutional_design_separation_of_powers.md) (*Institutional design, separation of powers, and authority custody*) and **CJS-5.125 §11** (*Accountability: distributed and proportional authority terms*) / **CJS-5.120 §7** (*Participation: quorum and participatory legitimacy terms*).

Failure integrity, intervention, and steward scaling co-apply through **corpus_joint_structure.md** (**CJS-5.105 (*operational cluster library (oDef)*), CJS-5.110, CJS-5.115, CJS-5.120, CJS-5.125, CJS-5.130, and CJS-5.135** (*operational cluster library (oDef)*) clusters) and the rest of this **CS-14.305** (*Critical system stewardship*) file. See **[CS-0.310](cs_00.310_scope_purpose_identifier_rules.md#operates-in-conjunction-with)** (*Scope, purpose, and boundary interface*).

Class C, L, and P still need proportional risk management. They do not need the full three-lines model unless scale, coupling, or dependency makes similar measures warranted under the ordinary classification and stewardship rules.

The checks that test how well oversight works are in [§10 Competency, succession, inspectable action, and oversight effectiveness](#cs-14305-10-competency-succession-inspectable-action-and-oversight-effectiveness): the oversight effectiveness review, the steward assurance review, and contest-integrity monitoring.


## CS-14.305 §12 Intervention trigger

*In plain terms: What happens when a steward cannot or will not meet these duties — outside intervention is activated to preserve function, recoverability, and rights.*

If a steward is unable or unwilling to maintain continuity as these obligations require, intervention and override must be activated.

- **How:** Activation uses **CJS-5.125 §14** (*intervention governance and override-authorization terms*), **CJS-5.135 §23** (*intervention and override integrity terms*), the related operational clusters in **corpus_joint_structure.md**, and Chapter Six Rights Floor routing.
- **Why:** The purpose is to preserve function, recoverability, and **Foundational Rights**.
- **Stewardship failure:** Failing to maintain the required operational integrity, transparency, or dependency reduction is a high-severity constitutional violation, in proportion to the affected class and the resulting risk or harm.


## CS-14.305 §13 Relationship to system classes

*In plain terms: Steward status follows the highest class you actually affect, not who holds title. You can be a Critical System Steward without owning the system.*

Steward status and system class fit together as follows:

- **Linked to class, not a second class:** Steward category is coupled to system class (A, B, C) through [§2 Classification as steward](#cs-14305-2-classification-as-steward) and [§3 Stewardship criticality levels](#cs-14305-3-stewardship-criticality-levels). It does not replace the system class and is not a second impact-class finding.
- **Ownership does not matter:** An organization may be a Critical System Steward if it materially affects continuity or integrity, whether or not it owns the system.
- **Look at the real dependency:** Judge criticality from actual dependency and substitutability, not from ownership, contract framing, or declared scope alone. Look across the whole dependency chain, including subcontractors, maintainers, and infrastructure providers.
- **Class L and Class P:** They stay outside this overlay unless reclassification under **CS-9.305 (*System classification machinery*) and CS-9.310** (*System classification machinery*) raises the affected system to Class C or higher and [§2 Classification as steward](#cs-14305-2-classification-as-steward) is met.


## CS-14.305 §14 Private chokepoints sentients depend on (access continuity and non-capture)

*In plain terms: Payments, identity, compute, messaging, hosting, and app distribution can become chokepoints without being governments. Where survival or rights run through them, cutoffs need notice, reasons, and an appeal.*

Some coordination layers can become **private chokepoints** even when they are not government bodies. Examples are payments, identity and credentials, core compute or model access, messaging and calls, hosting and DNS, application distribution, and search or discovery where switching costs are high.

Where a Class A, Class B, or Class C system or institution depends on such a layer for survival, healthcare, refuge, political participation, remedy, or non-degrading continuity of [personhood](../core_05.055_band_participation.md#personhood), operators and Critical System Stewards must keep access continuous. They must also keep the process fair enough to stop arbitrary or capture-driven cutoffs.

Duties scale with dependency and class:

- Publish acceptance criteria and refusal reasons in plain language.
- Give notice before a material cutoff, except where narrow **Necessity** requires immediate action.
- Keep emergency continuity options for survival-critical or Rights-Floor uses when fraud or abuse is not verified.
- Offer appeal, human review, and portability or export where lock-in would block remedy.
- Track and disclose patterns of uneven exclusion against protected or high-dependency groups.
- Coordinate with [**CI-6.205**](../corpus_institutions/ci_06.205_transparency_participation_accessible_pathways.md) (*Transparency, participation, and accessible challenge and service pathways*) and **CI-13.205** (*Procedure integrity, contestability, and secondary review*), so that governance and forum challenge routes stay practically usable.

**Safety, security, and abuse.** **Necessity** and **Proportionality** still allow narrow fraud, security, and abuse controls. The target is pretextual or concentration-driven denial, not forced service for materially harmful use. Read with **Article VI-D** (*Accessibility*), **Article XI-B** (*Expression*), **Article XI-F** (*Non-Imposition and Consent in Association*), **Article XIV-A** (*Security, Intelligence, and Covert-Power Limits*), **Article XXII-C** (*Non-Statelessness*), **Article XXI** (*Interoperability, Portability, and Exit Integrity*), [**Chapter One §9.1 Productive Capacity**](../core_01.005_values_principles.md#91-productive-capacity-instrumental-good), [**Chapter One §11 Market Structure**](../core_01.005_values_principles.md#11-market-structure), **CJS-5.130 §17** (*interoperability, portability, and exit-integrity terms*), and **`corpus_institutions.md` CI-6.255** (*Commons, cooperatives, mutual aid, and non-market community governance*) (commons and mutual-aid coordination).

Classification-governance disclosure, challenge, and reclassification for the dependent system stay in **[CS-9.305 Part A §7 classification governance, disclosure, and challenge](cs_09.305_system_classification_machinery.md#cs-9305-7-classification-governance-disclosure-and-challenge)**.


## CS-14.305 §15 Core characteristics (typical)

*In plain terms: The five traits that usually mark a steward: concentrated dependency, opacity risk, control over intervention, sensitivity to organizational decay, and no realistic replacement in time.*

Critical systems typically show these characteristics:

- **Dependency concentration:** A large share of continuity or recovery sits in one organization.
- **Operational opacity risk:** The organization can affect behavior or hide failures without immediate outside detection.
- **Intervention control:** It can enable, delay, or block intervention or recovery.
- **Continuity sensitivity:** Decay in the organization (staffing, governance, incentives, insolvency, capture) turns into risk to the system.
- **Low substitutability:** Replacement within survival-related timeframes is not feasible under normal or foreseeable conditions.


## CS-14.305 §16 Substitutability and dependency reduction

*In plain terms: Where the steward cannot be replaced, say so, explain why, add compensating controls, and work continuously at making the dependency smaller.*

Dependency reduction must be continuous, demonstrable, auditable, and proportionate to the dependency and the potential for harm.

**Where full substitutability cannot be achieved in the required time,** the steward must:

- disclose the nature, scope, and duration of the dependency
- justify why substitutability cannot be achieved under current and foreseeable conditions
- apply compensating controls, such as redundancy, external oversight, failover, and control partitioning
- provide heightened transparency, audit, and oversight in proportion to the risk
- periodically evaluate, test, and update its assessments, including under stress, degradation, and partial failure

**While substitutability cannot be achieved in operational and recovery timeframes,** the steward must actively reduce the dependency by:

- documenting, standardizing, and building for interoperability
- using knowledge, processes, and tooling that can pass beyond a single team or individual
- providing redundant infrastructure, capabilities, and recovery routes, unless that is demonstrably infeasible
- designing to minimize coupling, lock-in, and exclusivity


## CS-14.305 §17 Transparency and auditability

*In plain terms: Operational status, failure modes, and dependencies must be visible, independently auditable, and traceable to the organization's own actions.*

A steward must provide:

- visibility into operational status for integrity, into failure and degradation modes, and into dependencies and constraints
- independent audit and inspection in proportion to impact

The organization's own actions that affect system behavior must be traceable and attributable.


## CS-14.305 §18 Intervention and cooperation

*In plain terms: Even where the steward is also the operator, intervention must be possible from outside it — with real interfaces, timely response, and no obstruction.*

Even when the organization is the operator, it must provide internally separable intervention routes. Those routes must:

- respond in a timely way to authorized interventions, overrides, and recovery
- make interventions effective within times that fit the risk
- have clear interfaces with system operators, regulators and governance bodies, and emergency responders

The steward must not obstruct, delay, or degrade authorized interventions.


## CS-14.305 §19 Governance and incentive integrity

*In plain terms: Internal mechanisms must catch capture, corruption, and systemic negligence, and must not reward hiding failure.*

The organization's mechanisms must detect and reduce capture, corruption, and systemic negligence. They must not:

- create incentives that systematically conflict with integrity or safety
- make it possible to conceal failure, risk, or degradation

The structures that resist these pressures in the first place are in [§7 Structures that resist pressure and capture](#cs-14305-7-structures-that-resist-pressure-and-capture).


## CS-14.305 §20 Evasion and reclassification

*In plain terms: Splitting up, outsourcing, or restructuring does not shed the classification. Where dependency grows or substitutability falls, requirements rise.*

Classification follows the real dependency, however the organization is arranged:

- Fragmentation, outsourcing, or restructuring must not be used to evade classification.
- Where there is no viable substitute, treat the organization as inseparable for classification, governance, and accountability.
- Reclassify, or raise the requirements, where dependency grows beyond what was assessed, substitutability falls, or systemic importance rises because the wider ecosystem has changed.
- System integrity cannot be separated from institutional reality. Dependent organizations inherit responsibility in proportion to their dependency.
